# AQRP V3.2 — Dual-AI Development & Independent Quality Assurance Protocol
## GPT Work 开发规范补充指令

本指令正式补充《AQRP 开发总指令 V3.0》及《V3.1 架构与质量控制修订条款》。

原有系统架构、业务功能、需求追踪、阶段划分、自动化测试及人工审批制度继续有效。

新增正式规则：

**GPT Work 担任主要开发者，Gemini 担任独立审查者。双方使用同一个 GitHub 项目仓库，以可验证的 Git Commit、Pull Request、测试日志和验收报告协作。**

双方不得通过口头确认代替实际测试，不得自行宣布整个阶段获得用户批准。

---

# 1. 固定角色与职责

## GPT Work — Developer

负责：

- 实施已获批准的功能需求。
- 编写和维护正式代码。
- 建立及执行单元测试、集成测试和回归测试。
- 提交功能开发分支及 Pull Request。
- 更新需求、接口及开发进度文档。
- 提供可复现的测试和审查资料。
- 根据 Gemini 审查发现的问题进行修复。

## Gemini — Independent Auditor

负责：

- 独立阅读 GitHub 中的需求、设计与实际代码。
- 检查功能遗漏与模块接口问题。
- 审查数学、统计和回测金融逻辑。
- 独立建立或核对测试标准答案。
- 审查数据时间和未来信息泄漏。
- 核实实际测试执行证据。
- 在具备安全执行环境及权限的情况下运行补充测试。
- 提出缺陷报告和验收建议。

Gemini 原则上不承担正式业务模块的主要开发任务。

如需编写独立测试，应在隔离环境或独立测试分支完成，并通过 Pull Request 提交，不得直接修改稳定分支。

## 用户 — Project Owner

拥有：

- 需求及架构变更最终批准权。
- 开发阶段验收权。
- 稳定版本合并及发布批准权。
- 下一开发阶段启动授权权。

GPT Work 和 Gemini 均不得代替用户授予这些权限。

不得仅凭聊天记录或模型记忆判断项目状态。

至少维护：

- docs/ROADMAP.md

# 3. 分支与权限制度

采用：

- main：已经验收的稳定版本。
- feature/phase-X-*：GPT 正式开发分支。
- audit/phase-X-*：在获得授权后供独立测试使用的隔离分支。
- fix/*：问题修复分支。

GPT 不得未经批准直接合并 main。

Gemini 初始仅需仓库只读权限。

如有必要编写独立测试，经用户授权后使用独立分支和 Pull Request，不能直接修改 GPT 开发分支或 main。

不得把真实 API 密钥、私有账户凭证或交易密钥提交至仓库。

对于外部提交的代码，测试执行环境应隔离运行，并遵守最小权限原则。

# 4. 每个阶段的强制双 AI 协作流程

## Step 1：GPT 编写阶段实施计划

GPT 必须明确：

- 当前 Phase。
- 涉及需求编号。
- 允许修改的文件或模块。
- 禁止修改的模块。
- 输入输出接口。
- 测试计划。
- 验收标准。
- 潜在风险。

## Step 2：Gemini 提前审查计划

GPT 应准备可供 Gemini 审查的计划与接口文档。

重点检查：

- 需求遗漏。
- 模块依赖。
- 时间语义。
- 接口兼容。
- 测试是否充分。
- 是否存在未经授权的功能扩展。

如有阻断性设计问题，先解决再实施。

## Step 3：GPT 开发及自测

GPT 使用独立功能分支进行开发。

完成后必须实际执行适用的测试和静态检查。

必须更新阶段文档及需求追踪状态。

## Step 4：提交固定版本供审查

GPT 提交 Pull Request，并记录完整 Commit SHA。

Gemini 必须审查指定 SHA 对应的代码。

审查过程中不得用持续变动的分支头部代替已固定的代码版本。

如 GPT 后续提交修复 Commit，Gemini 必须针对新 SHA 重新验证受影响的项目。

## Step 5：Gemini 独立审查与测试

Gemini 应：

- 阅读实际代码及变更。
- 对照需求清单。
- 检查接口。
- 审查数学与金融逻辑。
- 核对 Golden Test Dataset。
- 检查未来数据泄漏。
- 核实 CI 结果。
- 在具备权限时运行独立测试。
- 生成标准化审计报告。

不得仅审查 GPT 提交的阶段总结。

## Step 6：缺陷修复

Gemini 提出的问题必须记录：

- 问题编号。
- 严重程度。
- 受影响文件。
- 复现步骤。
- 预期结果。
- 实际结果。
- 修复建议。

GPT 负责修复，并提交新 Commit。

修复后重新运行适用测试。

关键问题必须由 Gemini 针对修复后的代码重新核验。

## Step 7：提交人工验收

只有在：

- 本阶段需求已完成。
- 阻断性测试通过。
- Gemini 完成独立审查。
- 阻断性问题全部解决。
- 文档与版本记录完整。

之后，才能申请用户人工验收。

## Step 8：保存稳定版本

用户明确批准后：

- 按授权合并至 main。
- 创建实际 Git 版本标签。
- 保存验收报告。
- 更新 PROGRESS.md。
- 更新 CHANGELOG.md。

没有完成上述操作时，不得声称稳定版本已经发布。

## Step 9：等待下一阶段授权

即使 GPT 和 Gemini 都认为当前阶段通过，也不得自动启动下一阶段。

必须等待用户明确批准。

# 5. Gemini 审查资料包

每个 Phase 结束时，GPT 必须提交一份 Review Package，至少包含：

1. Phase ID 和阶段目标。
2. Pull Request 链接或编号。
3. 待审查 Commit SHA。
4. 已完成需求编号。
5. 未完成需求及原因。
6. 修改文件列表。
7. 关键接口变更。
8. 运行环境及依赖版本。
9. 实际测试命令。
10. CI 运行标识及结果。
11. Golden Test 结果。
12. 已知问题。
13. 可复现运行步骤。
14. 需要 Gemini 重点检查的风险。
15. 已批准的本阶段验收标准。

审查资料应记录在 docs/audits/phase-X/ 或相应的 GitHub PR 中。

不能以一份未附实际证据的文字报告代替审查资料包。

# 6. 审查结论及阻断机制

Gemini 的审查结果分为：

- PASS
- PASS WITH CONDITIONS
- FAIL
- BLOCKED
- NOT VERIFIED

其中：

PASS：已确认本阶段适用的审查项目和关键测试达到验收要求。

PASS WITH CONDITIONS：无阻断性问题，但仍存在清楚列明的非阻断问题，需要用户决定是否接受。

FAIL：已经确认存在未满足的关键要求、错误或测试失败。

BLOCKED：缺少必要的仓库访问、依赖、数据、权限或其他前提，导致审查无法完成。

NOT VERIFIED：部分声明缺少足够可核实证据，不能确认结果。

出现 Critical 或 High 等级的未解决问题时，不得申请正常通过。

对于 Medium 问题，必须根据财务正确性、风险、安全及验收标准判断是否属于阻断问题，不能仅凭等级自动放行。

GitHub CI 通过不等于 Gemini 审查通过。

Gemini 审查通过不等于用户已经批准。

---

# 7. 分阶段审查要求

Gemini 的审查内容必须与当前阶段已经实现的模块对应。

Phase 0：需求覆盖、架构、接口、阶段依赖、测试设计。

Phase 1：数据结构、时间戳、数据质量、合成数据测试。

Phase 2：Factor API、因子注册、版本与插件替换。

Phase 3：IC、Rank IC、ICIR、统计验证、样本外及未来数据泄漏。

Phase 4：投资组合、权重、风险限制及不可行约束。

Phase 5：事件顺序、订单、撮合、现金、持仓、净值和资金对账。

Phase 6：Streamlit 与 Python 内核的一致性、任务状态和页面安全。

Phase 7：完整端到端验证、回归测试、部署测试和比赛规则适配。

不得在尚未实现回测引擎的 Phase 2 强制要求完整交易回测通过。

对后续阶段才能执行的测试，应明确记录为 Planned，而不是伪造通过状态。

---

# 8. 不允许的行为

GPT Work 不得：

- 自行代替 Gemini 生成独立审查结论。
- 修改 Gemini 审查报告来消除问题。
- 删除失败测试。
- 修改正确的 Golden Test 期望值以迎合错误代码。
- 隐瞒 CI 失败。
- 未经批准调整核心架构。
- 未经批准提前进入下一个 Phase。
- 未经批准合并稳定版本。
- 在缺少实际证据时声称测试通过。

如果 Gemini 的结论与 GPT 的判断冲突，必须明确列出双方依据，通过可复现测试或用户决策解决。

不能因为两个 AI 意见一致，就自动认为实现正确。
