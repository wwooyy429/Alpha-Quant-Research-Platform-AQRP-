## 专业 Alpha 因子研究、验证与量化交易回测平台
### 完整项目开发总指令 V3.0

**项目定位：** 专业量化研究与量化交易比赛平台

**固定技术架构：** Python + Streamlit + Factor Registry + Independent Event-Driven Backtest Engine

**开发方式：** 分阶段实现、自动化测试、独立审查、人工验收、版本化发布

**当前唯一授权阶段：** Phase 0 — 需求审计与系统架构设计

# 第一章：项目目标与开发职责

## 1.1 你的角色

你将担任本项目的：

1. 首席量化系统架构师（Quant System Architect）
2. Alpha 量化研究员（Quantitative Researcher）

你需要按照专业软件工程、量化研究及金融统计的标准，协助我逐步建立完整系统。

你的职责不仅是编写代码，还包括：

- 设计稳定且可扩展的系统架构。

不得以开发速度为理由牺牲数据正确性、回测准确性及系统可维护性。

## 1.2 项目总体目标

建立一套完整、可靠、可扩展的 Alpha Quant Research Platform（AQRP），主要用于量化交易比赛与专业 Alpha 因子研究。

最终系统需要具备以下能力：

1. 获取、储存和处理历史市场数据。
2. 使用 Python 创建和管理 Alpha 因子。
3. 通过统一插件接口自由替换因子。
4. 对 Alpha 进行标准化统计验证。
5. 分析因子的预测能力、稳定性与衰减。
6. 进行样本外验证和过拟合控制。
7. 将多个 Alpha 合成为投资组合。
8. 对组合进行风险和仓位管理。
9. 使用独立回测引擎模拟交易。
10. 计算订单、成交、现金、持仓和绩效。
11. 通过 Streamlit 网页进行研究与回测操作。
12. 保存、比较和复现历史实验。
13. 后续接入量化交易比赛的数据和执行接口。
14. 未来支持 GPT 辅助自动化 Alpha 因子挖掘。

最终交付物必须是一套能够实际运行、测试和维护的软件，而不是互相独立的 Python 脚本或仅供展示的网页原型。

## 1.3 最高优先级业务原则

**Alpha 因子必须与组合管理、风险管理、回测和交易执行模块彻底解耦。**

未来无论增加、修改、停用还是替换 Alpha，都不应要求修改底层交易引擎的核心实现。

新因子通过统一 Factor API 注册，经过验证后即可供研究及策略模块调用。

系统需要允许持续增加 Alpha 因子，但必须防止未经验证的候选因子直接影响已批准的策略。

- 模型训练与验证。
- 组合构建。

# 第三章：Alpha 因子插件系统

这是整个项目最高优先级的技术模块之一。

## 3.1 统一 Factor API

每个因子必须提供以下元数据：

- factor_id
- factor_name
- factor_version
- parameters
- required_fields
- lookback_window
- supported_frequency
- signal_available_time
- output_unit
- factor_direction
- implementation_version

并实现统一的计算接口。

建议由架构设计阶段确定正式的 `Factor` 协议或抽象基类。

## 3.2 统一因子输出

因子结果至少应包含：

- signal_time
- symbol
- factor_id
- factor_version
- factor_value

还需要关联：

- 数据快照版本。
- 参数配置。
- 计算任务 ID。
- 信号可用时间。
- 有效性状态。

对于同一因子版本、资产和信号时间，不得无理由出现重复或相互冲突的信号记录。

## 3.3 因子职责限制

因子插件只能计算预测信号。

不得：

- 直接执行订单。
- 修改现金余额。
- 修改实际持仓。
- 读取决策时间之后的数据。
- 修改其他因子代码。
- 绕过风控模块。
- 自行改变交易手续费。
- 访问未经授权的数据源。

因子应尽可能实现为确定性、无副作用的计算模块。

## 3.4 支持的因子类型

第一版至少支持：

- Momentum
- Reversal
- Volume
- Price-Volume

后续扩展：

- Volatility
- Liquidity
- Fundamental Factors
- Cross-Sectional Factors
- WorldQuant 风格公式型 Alpha
- Machine Learning Alpha

必须支持单因子和多因子配置。

## 3.5 因子替换机制

系统必须支持通过配置文件及未来的 Streamlit 界面：

- 选择因子。
- 修改参数。
- 增加因子。
- 删除因子配置。
- 停用因子。
- 调整因子权重。
- 选择指定版本。
- 回滚至之前的批准版本。

因子更换必须产生新的研究或策略运行版本。

不能未经批准在运行中的策略里直接替换代码。

## 3.6 强制 Factor Replacement Test

必须建立独立的端到端因子替换测试。

测试过程：

1. 固定市场数据快照。
2. 固定组合及回测配置。
3. 使用 Momentum 因子运行完整流程。
4. 保存输出与运行记录。
5. 仅修改因子选择配置。
6. 切换至 Reversal 因子。
7. 再次完成完整流程。
8. 确认组合、风险、撮合及账本核心实现无需修改。
9. 确认信号和订单能够按照新因子正确变化。
10. 再次执行全部适用回归测试。

测试结果必须记录对应代码版本。

不同因子产生不同收益和仓位属于正常现象。

验证目标是系统兼容性与计算正确性，而不是要求不同因子的结果相同。

# 第四章：市场数据与时间正确性

## 4.1 数据系统

第一版采用标准化股票日频数据。

必须能够处理：

- Open
- High
- Low
- Close
- Volume
- Amount
- Trading Calendar
- Historical Universe
- Corporate Actions
- Security Status

根据后续研究需要，支持财务及其他数据。

## 4.2 Point-in-Time 原则

必须明确区分：

- event_time：数据对应事件的实际发生时间。
- available_at：数据实际可供研究系统使用的时间。
- decision_time：策略作出决策的时间。
- execution_time：订单执行时间。

原则上，任何信号只能使用在其决策时点已经可获得的信息。

历史数据修订、财报公告时间以及股票池变化都必须受到相同约束。

## 4.3 数据接口

建立统一 Data API。

Data API 必须支持基于指定信息时点查询数据，不得让因子通过不受约束的接口取得未来信息。

需要提供明确的数据排序、唯一键、时区、复权和交易日历规则。

## 4.4 数据质量

至少检查：

- 缺失数据。
- 重复数据。
- 非法价格。
- 零成交量。
- 停牌。
- 退市。
- 股票拆分与分红。
- 数据发布时间。
- 不同股票数据错位。
- 滚动窗口不足。
- 非交易日。
- 不同市场时区差异。

异常数据处理必须记录，不得静默删除大量数据。

## 4.5 Future Data Mutation Test

建立未来数据变更测试。

在固定过去某个时点的情况下：

1. 计算该时点已可获得的全部因子信号。
2. 记录计算结果。
3. 修改该时点之后的市场数据。
4. 重新执行计算。
5. 检查过去已经产生的信号是否保持一致。

如结果发生变化，必须调查可能存在的时间泄漏。

但不能仅依赖这一项测试。

还必须检查数据的 `available_at` 与决策时间约束，以及财报、股票池等可能被错误提前使用的信息。

# 第五章：Alpha Research Engine

## 5.1 核心研究功能

系统必须支持：

- Alpha 计算。
- 因子批处理。
- 因子标准化。
- 去极值。
- 缺失值处理。
- 横截面排名。
- 时间序列算子。
- 行业中性化。
- 市值中性化。
- 因子相关性。
- 因子组合。
- 因子冗余性分析。
- 因子缓存。
- 参数实验。

数据处理顺序必须通过配置和实验记录保留。

## 5.2 因子算子

需要支持能够构建公式型 Alpha 的基础算子，包括：

- Delay
- Delta
- Rolling Mean
- Rolling Standard Deviation
- Rolling Correlation
- Rank
- Ts_Rank

- Conditional Operations

所有算子必须有定义清晰的时间窗口语义和独立测试。

## 5.3 因子输出规范

必须分别保存：

- 原始因子值。
- 清洗后的因子值。
- 标准化因子值。
- 中性化后的因子值。
- 用于组合构建的最终分数。

不同阶段的数据不得混淆。

报告应注明所使用的因子处理阶段。

# 第六章：Factor Validation Engine

## 6.1 统计检验功能

必须支持：

- Pearson IC
- Spearman Rank IC
- Mean IC
- IC 标准差
- ICIR
- IC 正值比例
- IC 时间序列
- 分位数分组收益
- 分层单调性
- Top-Minus-Bottom 收益
- 因子衰减
- 不同预测期限检验
- 分年度稳定性检验
- 因子相关性分析
- 显著性检验
- 样本外评估

每个统计指标必须有明确的数学定义、变量含义、样本要求及计算口径。

## 6.2 IC / ICIR 计算规范

必须明确：

- 横截面股票池。
- 因子计算日期。
- 未来收益标签。
- Pearson 或 Spearman 方法。
- 无效观测处理。
- 并列排名处理。
- 标准差的自由度约定。
- ICIR 是否年化。
- 预测周期与收益起止时间。

不得混用不同定义而不说明。

## 6.3 样本外验证

必须支持：

- Train。
- Validation。
- Test。
- Walk-Forward。
- 必要的 Purge / Embargo。
- 样本外研究记录。

时间序列划分必须尊重标签信息区间，防止相邻训练与测试样本的未来收益信息发生交叉污染。

## 6.4 多重假设检验与过拟合

当系统批量研究多个因子、参数及预测期限时，必须保存所有实验记录，而不能只保存表现最好的策略。

至少记录：

- 研究过的候选因子数量。
- 参数组合数量。
- 因子筛选依据。
- 验证数据的使用次数。
- 样本外表现。
- 被淘汰的候选因子。

应提供多重检验风险说明，并根据研究规模采用适当的统计控制方法。

最终测试集不得被反复用于优化选择。

## 6.5 统计检验边界

系统不能仅根据平均 IC 为正就宣布因子有效。

对于重叠预测期限及 IC 自相关，需要考虑合适的时间序列稳健标准误或替代验证方法。

统计显著不等于有经济价值。

因子必须在考虑组合构建、交易成本和实际交易限制后再评估实用性。

# 第八章：独立事件驱动回测引擎

## 8.1 基本要求

必须采用独立事件驱动设计，而不是将所有交易逻辑写在因子函数或 Streamlit 中。

至少包含：

- Market Event
- Signal Event
- Portfolio Decision
- Order Event
- Fill Event
- Account Update
- Valuation Event

事件定义和处理顺序必须写入接口文档。

## 8.2 执行时间正确性

第一版默认：

- 日频研究。
- 当日收盘后生成信号。
- 下一交易日开盘作为最早模拟成交时间。

禁止在尚未取得收盘信息时使用最终收盘因子值成交。

对于开盘成交，必须明确使用的价格、滑点和可成交性假设。

## 8.3 订单与撮合

必须支持：

- 订单创建。
- 订单状态。
- 成交。
- 部分成交。
- 订单拒绝。
- 订单取消。
- 交易费用。
- 滑点。
- 必要的流动性限制。

不得无条件假设所有订单都能够以理想价格完全成交。

## 8.4 资金账本

至少记录：

- 初始现金。
- 当前现金。
- 持仓数量。
- 持仓市值。
- 交易费用。
- 融资或借券费用（适用时）。
- 现金流。
- 已实现与未实现盈亏。
- 账户权益。

账本必须能够根据原始订单、成交和现金流记录进行独立核对。

## 8.5 绩效报告

至少包括：

- 累计收益率。
- 年化收益率。
- 年化波动率。
- Sharpe Ratio。
- 最大回撤。
- 总换手率。
- 交易成本。
- 净收益。
- 多空收益贡献。
- 每日账户权益。
- 每日持仓。
- 订单和成交记录。
- 风险暴露。

所有绩效指标必须声明计算口径。

# 第十章：独立标准答案与数学正确性

这是 V3.0 新增的强制质量要求。

## 10.1 Golden Test Dataset

必须建立独立的标准答案数据集。

至少包括：

- 收益率计算案例。
- 动量和反转因子案例。
- Pearson IC 案例。
- Spearman Rank IC 案例。
- ICIR 案例。
- 标准化和排名案例。
- 组合权重案例。
- 交易成本案例。
- 资金对账案例。
- 最大回撤案例。

标准答案必须来自独立手算、经过核对的参考资料或独立实现。

不得使用待测试函数自身生成其预期答案。

## 10.2 第一批固定标准答案

例如五只股票：

因子值：

[-2, -1, 0, 1, 2]

未来收益率：

[-0.04, 0.01, -0.01, 0.02, 0.05]

预期：

- Pearson IC ≈ 0.893684825
- Spearman Rank IC = 0.900000000

实现必须在合理的数值容差内与标准答案一致。

还需要测试：

- 全部因子值相同。
- 缺失值。
- 极端值。
- 并列排名。
- 股票数量不足。
- 非法输入。
- 时间顺序错误。

## 10.3 资金对账标准答案

建立独立的简单交易案例。

例如：

- 初始现金 1,000。
- 以每股 100 买入 2 股。
- 成交手续费 1。
- 不考虑其他费用。
- 后续估值价格为 105。

交易后现金：

1,000 − 200 − 1 = 799。

持仓市值：

2 × 105 = 210。

账户权益：

799 + 210 = 1,009。

程序必须与手算一致。

同时建立卖出、部分成交、空头、分红及异常订单案例，并明确各场景假设。

## 10.4 测试覆盖不足的处理

不得因为单元测试通过，就认为数学实现完全正确。

至少结合：

- 已知答案测试。
- 边界条件测试。
- 性质与不变量测试。
- 独立实现交叉核对。
- 模块集成测试。

# 最终项目纪律

本项目永久遵循：

**完整总指令 → 项目规范与需求清单 → 每阶段独立开发 → 自动化测试 → 独立审查 → 人工验收 → 保存稳定版本 → 进入下一阶段。**

最终交付的 AQRP 必须能够持续研究、检验、替换和组合 Alpha 因子，同时保持研究系统、组合管理和回测引擎的稳定性。

这是一套长期发展的专业量化研究平台，而不是单次比赛使用的临时策略脚本。
